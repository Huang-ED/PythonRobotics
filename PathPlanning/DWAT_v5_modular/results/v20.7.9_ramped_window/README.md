# v20.7.9 — making the dynamic window and the prediction horizon agree

**What it was built for.** v20.7.9 exists to solve the open-water *"ego is
overtaken"* problem: `owenc_overtaken_ego` and `owenc_overtaken_ego_fast` were
the only two of the 11 open-water encounter cases that did not reach the goal,
both aborting on iteration 0. Reconciling the dynamic window with the
prediction horizon is the *means*; fixing those two cases is the *goal*.
Everything below follows from it.

Status: **prototype, not a replacement for v20.7.8-2.** It fixes the two
`owenc_overtaken_ego*` failures and regresses nothing tested, but it also
removes a safety guard without replacing it — see
[section 5](#5-the-open-problem-the-abort-guard-is-now-unreachable) before
adopting it.

Investigated 2026-09-07 → 2026-09-10. Baseline throughout is **v20.7.8-2**.

- Code: `PathPlanning/DWAT_v4_st/dwa_ramped.py`
- Config: `configs/algorithm/v20.7.9.json`, variant
  `configs/algorithm/v20.7.9/predT5-ramped.json`
- Runs: `runs/v20.7.9/`
- Figures, all in `../openwater_suite/`: `overtaken_failure.png` (mechanism
  and horizon sweep), `overtaken_frame0.png` (the frame the aborted run would
  have drawn), `overtaken_target_tracks.png` (both planned target legs)

## 1. The bug it was built to fix

`owenc_overtaken_ego` and `owenc_overtaken_ego_fast` abort on **iteration 0**
with `No best trajectory found`.

The dynamic window admits only the velocities reachable in one `dt`, then
scores each by holding that velocity for the whole `predict_time_obstacle`.
At a 30 s horizon those two statements contradict each other. From rest the
window offers `v ∈ [0, 0.02]`, so the planner predicts itself travelling
**0.60 u in 30 s** when it can really cover **14.40 u**. A target closing from
astern sweeps through every candidate, all 243 score `inf`, `best_index` stays
-1, and the planner aborts.

The reachable set it plans within is *smaller than the ship itself* (0.6 u
across, hull 1.2 u) — see `overtaken_frame0.png`, panel 3.

Two error strings, two distinct code paths, and the distinction matters:

| message | fires when | in these cases |
|---|---|---|
| `No admissible (v, ω) pairs` ([dwa_average_weighted_side.py:513][a]) | the admissibility `continue` rejected everything | predT5, iteration 875 |
| `No best trajectory found` ([:530][b]) | candidates were admissible but every `final_cost` was `inf` | predT30, iteration 0 |

[a]: ../../../DWAT_v4_st/dwa_average_weighted_side.py#L513
[b]: ../../../DWAT_v4_st/dwa_average_weighted_side.py#L530

## 2. Shortening the horizon is not the fix

It only lowers the spawn distance that triggers the abort. The condition is

```
predT >= (gap - 1.15) / (v_target - 0.02)
```

Measured iteration-0 survival, target dead astern at 0.6 u/s (% of candidates
with a collision-free prediction):

| spawn gap | predT5 | predT10 | predT15 | predT20 | predT30 |
|---|---|---|---|---|---|
| 4.0 u | 27% | 0% | 0% | 0% | 0% |
| 6.0 u | 100% | 0% | 0% | 0% | 0% |
| 8.0 u | 100% | 100% | 0% | 0% | 0% |
| 10.55 u | 100% | 100% | 100% | 0% | 0% |
| 14.0 u | 100% | 100% | 100% | 100% | 0% |

`predT10` still breaks on any target spawning within ~7 u astern, `predT5`
within ~4 u.

**The two failures are opposite ends of one tension.** You need a *long*
horizon to see a 0.1 u/s overtake at all — at predT5 the ego cruises straight
for 87 s and only reacts when the target is 0.065 u away. But the naive long
horizon paralyses the planner at low speed. Shortening trades one for the
other; only fixing the model gets both.

## 3. The fix

A sampled `(v, ω)` becomes a **target** the ego accelerates toward, not a
velocity it teleports to. Four config changes against v20.7.8-2:

| key | value | why |
|---|---|---|
| `dwa_module` | `...dwa_ramped` | new module, `dwa_consistent.py` pattern |
| `v_window_ramp_time` | `2.5` | v window spans what the horizon can reach (`max_speed/max_accel`). At rest: `[0, 0.50]` not `[0, 0.02]`; 30 s reach 14.40 u not 0.60 u |
| `ramped_rollout` | `true` | setpoint approached at `max_accel`, in rollout **and** execution. Without this a widened window would let the sim jump 0 → 0.5 u/s in one `dt`, violating `max_accel` |
| `no_admissible_fallback` | `least_bad` | when every candidate is `inf`, keep the one furthest from contact instead of raising |
| `v_resolution` | `0.05` | the v window went from 3 samples to the full range; coarsening keeps the count near baseline (891 vs 243, ~3.7× slower) |

The search stays a **2-D grid** over `(v, ω)` — one setpoint per candidate,
acceleration profile generated by the rollout. Cost grows *linearly* with
sample count. Exponential blow-up only arises if you search *sequences* of
commands; this deliberately does not.

At iteration 0 the window becomes `[0.00, 0.50]` and **596 of 891** candidates
are collision-free, where before **0 of 243** were.

## 5. The open problem: the abort guard is now unreachable

**This is the reason v20.7.9 is not yet a drop-in replacement.**

`predT5` is **meant to fail.** It exists to demonstrate that a short prediction
horizon is insufficient — that the planner cannot see a 0.1 u/s overtake
coming and will not manoeuvre in time. Under both versions it fails, and that
is the correct and intended outcome. Nothing below disputes that.

What changed is the **manner** of the failure, and only that:

| | v20.7.8-2 predT5 | v20.7.9 predT5 |
|---|---|---|
| outcome | abort, iteration 875 | **collision, iteration 881** |
| error | `No admissible (v, ω) pairs` | none — `collision_event` recorded |
| final clearance | 0.065 | **−0.034** (centre 1.148 vs threshold 1.15) |

Run: `runs/v20.7.9/predT5-ramped/encounters/owenc_overtaken_ego__20260910_164626/`

### Mechanism

The admissibility test is a braking-distance constraint:

```
reject (v, ω) if   v² + 2·a·v·dt  >  2·a·dist
```

At `v = 0` this reduces to `0 > 0.4·dist`, which is **never true**. So `v = 0`
is always admissible. The baseline's narrow window at cruise offered only
`v ∈ [0.48, 0.50]`, every one of which failed the check — hence the abort.
v20.7.9's window always contains `v = 0`, so something is always admissible and
**the `No admissible (v, ω) pairs` guard has become unreachable**.

The planner then does the worst available thing: it slows
(0.50 → 0.40 → 0.38 → 0.36) while a 0.6 u/s ship closes from dead astern, and
is run down.

### What this does and does not mean

**The abort guard is gone everywhere, not just at `predT5`.** This is the part
that matters. `v = 0` being always admissible is a property of the *widened
window*, not of any particular horizon — so the `No admissible (v, ω) pairs`
guard is unreachable in every v20.7.9 configuration, `predT30` included.
`predT5` is merely the setting where the planner actually reaches a cornered
state and the loss becomes observable. "`predT5` is supposed to fail" therefore
does **not** contain the problem: the guard is missing from the shipping config
too, where it has simply never been called on.

**The baseline's abort was not a save.** It fired at 0.065 u clearance, a
fraction of a second from contact, with a faster ship overlapping from astern.
It was a *report* that no certifiable move remained, not a successful
avoidance. So v20.7.9 did not cause a crash that v20.7.8-2 prevented — it
removed the warning that one was imminent. Whether the baseline could still
have escaped from that state is **untested**; it would need a run of
v20.7.8-2 at `predT5` with `least_bad` enabled and the narrow window kept.

That is a narrower claim than "v20.7.9 fails worse", and it is the accurate
one. It is still a regression: a planner that cannot tell you it is out of
options is worse than one that can, and silent contact is the worst possible
way to find out.

**It was the window widening, not `no_admissible_fallback`, that did this.**
The fallback only catches the *other* guard (`No best trajectory found`).
**The cost function does not know that slowing is dangerous when overtaken
from astern.** The braking-distance test is built for static obstacles,
where stopping is always safe. Against a faster ship approaching from behind,
stopping is the one thing guaranteed to cause contact. This is latent in
v20.7.8-2 too — it stays hidden only because the narrow window cannot reach
`v = 0` from cruise in one step.

### Scope

The observed collision is `predT5`-only. At `predT30` `overtaken_ego` reaches
goal with 1.15 clearance, and all 11 encounter cases plus both passing crowd
scenes are unaffected. But as above, the *missing guard* is not `predT5`-only —
it is absent from `predT30` as well, and no test in the suite currently
exercises it. That is the gap to close.

### Suggested direction (not implemented, not validated)

A **stern-sector guard**: when a faster target is inside the astern sector and
closing, penalise deceleration rather than rewarding it. This is a cost-function
change, separate from the window/rollout fix, and it needs its own scenario —
none of the 11 open-water cases would catch it, because at `predT30` the
planner never chooses to slow.

Open questions for that work:

- Should the `No admissible (v, ω) pairs` guard be restored in a form the wide
  window cannot bypass (e.g. admissibility evaluated against *predicted*
  obstacle positions rather than current ones)?
- `closest_obstacle_on_curve` treats dynamic obstacles as **stationary at their
  current position** and checks the entire arc "without time/span limitations".
  Is a braking-distance test meaningful at all for moving targets?
- Does `least_bad` want a better ranking than max-min-clearance — e.g. latest
  time-to-contact, which would prefer fleeing over stopping?

## 6. Known limitations of the prototype

- The **yaw window is still one `dt`.** Unlike `v`, a yaw rate genuinely *is*
  reachable within one `dt` (`max_delta_yaw_rate · dt` equals the whole
  window), so it is already self-consistent. Widening it toward
  horizon-reachable rates is the same change and has not been made.
- **`closest_obstacle_on_curve` still assumes a constant-velocity arc** for
  admissibility and static-obstacle cost, so it under-estimates travel during
  the ramp.
- `dwa_ramped.motion` is called by the runner as `motion(x, u, config.dt)` —
  three positional args, no config. `dwa_control_merged` runs immediately
  before it each iteration and stashes the actuator limits in a module-level
  `_LIMITS` dict for `motion` to pick up. Contained and documented, but it is
  the prototype's one wart.

## 7. Reproducing

```bash
# the fix
python -m PathPlanning.DWAT_v5_modular.main \
    --scenario owenc_overtaken_ego --algorithm-config v20.7.9

# the degraded variant that collides
python -m PathPlanning.DWAT_v5_modular.main \
    --scenario owenc_overtaken_ego --algorithm-config v20.7.9/predT5-ramped

# score against v20.7.9's own obstacle-free baseline
python PathPlanning/DWAT_v5_modular/adapters/encounter_report.py \
    --baseline-log runs/v20.7.9/baseline/openwater_baseline__20260909_040103/log_details.json \
    --manifest PathPlanning/DWAT_v5_modular/configs/scenarios/encounters/owenc_manifest.json \
    --runs "runs/v20.7.9/encounters/owenc_*/log_details.json"
```

A case takes ~40 min at v20.7.9 (891 candidates) vs ~11 min at v20.7.8-2.

## 8. Incidental fix — config path resolution

`find_config_by_name` did `stem = Path(name).name`, **discarding the directory
component** before searching by bare filename. Its own error message
("Ambiguous config name ...; Pass a fuller path") therefore described something
impossible — a fuller path was thrown away. Adding
`v20.7.9/predT5-ramped.json` exposed this by making the bare name `predT5`
ambiguous with `v20.7.8-2/predT5.json`.

It now honours a directory-qualified name before falling back to the bare
search, so the canonical `<version>/<variant>` form that
`version_from_config` documents finally round-trips:

| input | resolves to |
|---|---|
| `predT5` | `v20.7.8-2/predT5.json` |
| `predT5-ramped` | `v20.7.9/predT5-ramped.json` |
| `v20.7.9/predT5-ramped` | ✅ canonical, new |
| `v20.7.8-2/predT10` | ✅ canonical, new |
| `v20.7.8-2_predT10` | ✅ legacy flat form, unchanged |
| `encounters/owenc_head_on` | ✅ scenarios benefit too |

String handling is append-not-replace (`with_name`, not `with_suffix`), because
these version names contain dots: `Path("v20.7.8-2").with_suffix(".json")`
would yield `v20.7.json`.

The variant is named `predT5-ramped` (hyphen, not underscore) because
underscore is overloaded here as the legacy version/variant separator
(`v20.7.8-2_predT10`), so `predT5_ramped` could be misread as version
`predT5`, variant `ramped`.
