The Ramped Window

The dynamic window admits only what is reachable in one control step, then scores each candidate as if it were held for thirty seconds. For a ship those two sentences contradict each other badly enough that the planner stops. This is what goes wrong, what fixes it, and whether any of it is new.

01

Two statements that contradict each other

Classic DWA builds its velocity window from the acceleration limit over a single control step:

window = [ v − max_accel·dt ,  v + max_accel·dt ]     dt = 0.1 s

At rest, with max_accel = 0.2, that window is [0, 0.02] — a fifth of a percent of what the ship can do. Each sampled velocity is then scored by holding it constant for the full 30 s prediction horizon.

So the planner evaluates a future in which it crawls at 0.02 u/s for half a minute. The real ship, starting from that same standstill, covers 14.40 u in 30 s. The escape it needs — open the throttle and pull away — is not merely scored badly. It is unrepresentable: no point in the sample space corresponds to it.

Now put a faster ship dead astern. Every candidate the planner can represent is slower than the overtaking target, so the target sweeps through all of them; every predicted trajectory collides; every cost becomes inf; best_index stays −1 and the run aborts on iteration 0 with No best trajectory found. Two of the eleven open-water encounter cases failed exactly this way.

02

The fix: sample a setpoint, not a velocity

One idea, applied in two places that must agree:

  1. Size the window to the horizon, not to one step. v_window_ramp_time replaces dt in the window construction. Set to max_speed / max_accel = 2.5 s, the window at rest becomes [0, 0.50] — the whole speed range.
  2. Roll out the acceleration you just promised. ramped_rollout integrates the sampled pair as a setpoint approached at max_accel, in the prediction and in execution. Without it, widening the window would let the simulated ego jump 0 → 0.5 u/s in one dt and silently violate its own acceleration limit.

The motion model becomes a first-order lag against the actuator limit rather than a direct assignment:

dv = u[0] − x[3]
x[3] += clamp(dv, −max_accel·dt, +max_accel·dt)     # was: x[3] = u[0]
dw = u[1] − x[4]
x[4] += clamp(dw, −max_delta_yaw_rate·dt, +…)

A sampled (v, ω) now means "the speed I am aiming for" instead of "the speed I will have next step". The search space keeps the same shape — a 2-D grid — and the acceleration profile is generated by the rollout rather than searched over.

03

Shortening the horizon is not the fix

The obvious cheap alternative is to predict less far ahead, which does make the abort go away. It does so by lowering the spawn distance at which it triggers, not by removing it. Survival at iteration 0 follows a clean staircase:

The two failures are opposite ends of one tension. You need a long horizon to see a 0.1 u/s overtake at all; the naive long horizon paralyses the planner at low speed. Shortening trades one for the other — only fixing the model gets both.

05

Why this stays computable

The honest alternative to "one command held for the horizon" is to search sequences of commands. With 891 samples per step and 300 control steps in a 30 s horizon at dt = 0.1, a depth-k search costs 891k:

Search depthSequencesWall-clock for one case
1 — today8.9 × 10²40 min
27.9 × 10⁵25 days
37.1 × 10⁸60 years
300 — full horizon10⁸⁸⁵—

For scale, the observable universe holds roughly 10⁸⁰ atoms. Even depth 2 is off the table for a suite that re-runs.

The ramped rollout is a cheap approximation of that search. It does not abandon multi-step manoeuvres — it restricts them to a one-parameter family: ramp toward a setpoint at max_accel, then hold. Cost stays linear in sample count and constant in horizon length, while still representing the accelerate-away escape that the one-step window could not express at all. Any future feasibility test should preserve that property: a closed-form or single-rollout criterion, never a tree.

06

What it quietly broke

This is the part worth carrying into any write-up, because it is an interaction between the fix and a piece of classical DWA that nobody touched.

DWA's admissibility test keeps only velocities from which the robot can brake to rest before the nearest obstacle on that curve:

reject (v, ω)  if   v² + 2·a·v·dt  >  2·a·dist

At v = 0 this reduces to 0 > 2·a·dist, which is never true, so v = 0 is always admissible. The baseline's narrow window at cruise offered only v ∈ [0.48, 0.50], all of which could fail the check — and when they all did, the planner raised a hard abort. The widened window always contains zero. So something is always admissible, and that abort guard became unreachable in every configuration.

What the planner does instead is the worst available thing: it slows — 0.50 → 0.40 → 0.38 → 0.36 — while a 0.6 u/s ship closes from dead astern, and is run down.

The braking criterion is not merely conservative here — it is inverted. It was built for static obstacles, where stopping is always safe. Against a faster vessel overtaking from astern, stopping is the one action guaranteed to cause contact. Backward reachability from the baseline's own cornered state showed an escape did exist: v = 0.500 with a 32% starboard turn holds +0.0173 u of clearance, where braking straight ahead gives −0.5060 u. The surviving manoeuvre needs more speed plus a turn — and the admissibility test discards exactly that set first, then the planner correctly reports it has none.
A load-bearing coincidence. The window reaches v = 0 from any state only because v_window_ramp_time = 2.5 is exactly max_speed / max_accel = 0.5 / 0.2. That is a configuration convention, not a code invariant. Set the ramp to 2.0 and the floor at cruise becomes 0.1, zero leaves the window, and the guard becomes reachable at some speeds and not others — the worst of both worlds. Worth stating explicitly in any paper that reports this window.
07

Is any of this new?

Taking the mechanism and the findings separately, because they land very differently.

The ramped window itself: not novel.

It is a rediscovery of Trajectory Rollout, which has shipped in ROS base_local_planner since 2008 as the sibling algorithm to DWA. The wiki states the distinction in the terms this work arrived at independently:

Trajectory Rollout samples from the set of achievable velocities over the entire forward simulation period given the acceleration limits of the robot, while DWA samples from the set of achievable velocities for just one simulation step. ROS wiki · base_local_planner

The source is blunter still. In simple_trajectory_generator.cpp the two algorithms are separated by a single boolean, which toggles the window extent and the rollout together:

continued_acceleration_ = ! use_dwa_;

if (use_dwa_) {
  max_vel[0] = min(max_vel_x, vel[0] + acc_lim[0] * sim_period_);  // one control step
} else {
  max_vel[0] = min(max_vel_x, vel[0] + acc_lim[0] * sim_time_);    // the whole horizon
}

use_dwa_ = false is v_window_ramp_time plus ramped_rollout — the same two knobs, coupled for the same reason: widening the window without ramping the rollout would violate the acceleration limit. The header comment even gives the worked example — DWA samples 0→0.2 m/s where trajectory rollout samples 0→1 m/s, "respecting the acceleration limit, so it gradually increases velocity."

Has anyone folded it into DWA proper?

No — and that gap is real and uninteresting at once. The two changes are the DWA↔Trajectory Rollout distinction, so adding them to DWA does not yield a DWA variant: it converts DWA into Trajectory Rollout. Nobody added it because nobody needed to; you flip a flag.

Searched and ruled out: DWPP (2026) keeps a single-timestep window and is an analytic pure-pursuit variant; Missura & Bennewitz (ICRA 2019) change the collision model, not the sampling; TS-DWA (2024) changes where in the window it samples, not its extent; Global DWA (1999) and Convergent DWA (2005) address navigation functions and stability. The nearest neighbour is an enhanced DWA for UUVs (2026) arguing that inertia and actuator limits mean velocity candidates "cannot be generated arbitrarily" — worth reading in full.

Scope of the equivalence — state it carefully or a reviewer will correct you. One flag separates the two sampling modes of ROS's shared trajectory generator. It does not mean the two ROS packages differ only there — dwa_local_planner uses the modern critic architecture (SimpleScoredSamplingPlanner over Oscillation, Obstacle, GoalFront, Alignment, Path, Goal and Twirling cost functions) while base_local_planner scores inline. Nor does it hold for the published algorithms: Fox, Burgard & Thrun (1997) and Gerkey & Konolige (2008) are separate lineages with different objective functions. The equivalence is a property of ROS's unified reimplementation, not a theorem.

The find that changes the target of §06

Looking for the braking-admissibility test in ROS's DWA — v² + 2·a·v·dt > 2·a·dist, the Stage 1 veto — turns up nothing. It is absent from dwa_planner.cpp, and ObstacleCostFunction does something else entirely:

if we're over a certain speed threshold, we'll scale the robot's footprint to make it either slow down or stay further from walls ROS · obstacle_cost_function.cpp

That is scale = max_scaling_factor · ratio + 1.0 — velocity-proportional footprint inflation. A soft geometric heuristic, with nothing resembling v ≤ √(2·d·a_brake) anywhere in it.

The most widely deployed DWA implementation dropped the admissible-velocity constraint, and replaced the veto with a soft cost. This arrives at §06's argument from an unexpected direction. The braking test is not "what DWA does" — it is what the 1997 paper specified and what this codebase's v4 lineage inherited. In practice it was already retired, and the replacement is a penalty rather than a hard rejection, which is exactly the direction OPEN_PROBLEMS §3(a) proposes. That makes the Stage 1 critique a narrower and far more defensible target, and means it no longer has to be argued from first principles.

So: do not build a paper's contribution on the mechanism. A reviewer who knows the ROS navigation stack will recognise it immediately, and the honest framing — we independently rederived Trajectory Rollout and show why it is mandatory rather than optional in the maritime regime — is much stronger than a novelty claim that will not survive review. What surrounds the mechanism is a different matter.

Not novel Sampling over the horizon

Trajectory Rollout, 2008 — one boolean in the ROS source. Also standard in any MPC with input-rate constraints.

Not novel The braking admissibility test

Canonical to the 1997 DWA paper — but absent from ROS's DWA, which replaced it with speed-scaled footprint inflation.

Weak / incremental "DWA struggles with dynamic obstacles"

Extensively covered — Missura & Bennewitz (ICRA 2019); the maritime DWA literature is already sizeable.

Defensible Counterexample to standing guidance

ROS recommends DWA over Trajectory Rollout because "in practice they perform similarly". Here they do not: abort at iteration 0 versus 1.15 u clearance.

Defensible Infeasibility, not degradation

The wiki's caveat is an unquantified aside. This is a hard abort with a closed-form trigger condition — a different failure class.

Defensible Reachable set smaller than the hull

0.60 u of reachable travel for a 1.2 u vessel — a 24× underestimate, and a vivid instance of the ROS caveat.

Strongest Braking admissibility is inverted astern

Not "too conservative" — it selects the one fatal action and deletes the unique surviving manoeuvre. Measured, not argued.

Where the publishable contribution actually sits

Not in the window. In the observation that DWA's two filters model different physics, and that the feasibility filter is the wrong one on three independent axes: it freezes obstacles that the cost function extrapolates, it used a circumscribed disc where the cost function uses a capsule, and it scans unbounded arc length where the cost function respects a horizon.

Updated 2026-09-15 (194aacf). The hull axis is now closed: closest_obstacle_on_curve honours robot_collision_shape in all three of its branches, disc verified bit-identical. Two axes remain open, plus a newly found one — the function misreports an obstacle it is already touching (OPEN_PROBLEMS item 10).

For an elongated, low-acceleration vehicle every one of those is severe, and the middle one was measurable at 3.16× hull inflation abeam — though only 0.513 m along the bow, since a capsule's bow still reaches (L−W)/2 ahead of the hull centre. That distinction matters: the bow is the direction a braking test cares about. That is a coherent critique of the classical formulation as applied to ships, with a concrete remedy — move the CPA that already exists in the cost function onto the feasibility side and retire the braking test, as ROS's own DWA effectively already has.

Suggested framing. Position the ramped window as necessary preparation: cite Trajectory Rollout and Gerkey & Konolige, show the maritime regime makes it non-optional, and add the counterexample to the "they perform similarly" guidance — that much is publishable as a supporting result. Then spend the paper on the feasibility/cost inconsistency and the inverted braking criterion, which is where the genuinely new material is. The negative result in §06 — that fixing the window silently disabled a safety guard — is a good honest inclusion and reviewers tend to reward it.
Three gaps to close before submission. The backward-reachability grid that produced the escape numbers is not in the repository, so the headline evidence for the inverted-braking claim cannot currently be reproduced. The strongest AIS case for the braking critique, ny_synth_00, is still unproven — 287 pruned candidates have never been scored. And the prior-art sweep behind this section is English-language and largely abstract-level for paywalled venues; the sizeable Chinese-language 改进DWA literature warrants a CNKI pass before any novelty claim is committed to.
